# تصاویر گموریا — سیاست، منبع و جایگزینی

این سند پاسخ سه پرسش است: **این عکس‌ها از کجا آمده‌اند؟ چرا این‌طور؟ و اگر عکس واقعی داشتیم، چه چیزی عوض می‌شود؟**

---

## ۱. قاعده

> هیچ عکسی با واترمارک، منبع نامعلوم یا مجوز مشکوک در موزه منتشر نمی‌شود.

در محیط فعلی هیچ سرویس تصویر دارای مجوز و هیچ فایل عکس واقعی از مجموعه وجود ندارد. بنابراین — طبق دستور پروژه — از **تصاویر جایگزین محلی و قابل تعویض** استفاده شده است: نُه تصویر تولید‌شده برای همین پروژه، بدون واترمارک، بدون متن، بدون برند، و با یکدست‌بودن بصری (ماکرو، نور ویترین، پالت اُبسیدیَن/زمرد/طلای عتیقه).

**این تصاویر دادهٔ علمی نیستند.** هیچ‌کدام ادعا نمی‌کنند نمونهٔ خاصی از مجموعه‌اند: زیر تصویر معرفی موزه صریحاً نوشته شده «تصویر جایگزین تا زمان ثبت عکس‌های اصلی مجموعه»، و کارت‌های نمونه (که از پایگاه داده می‌آیند) تا وقتی عکس واقعی نداشته باشند، به‌جای تصویر جعلی، حرف اول نام شیء را در یک ویترین ساده نشان می‌دهند.

## ۳. زنجیرهٔ ساخت

```
public/images/source/*.png        ← فایل‌های مادر (۱۹ MB، در git نیست)
        │  npm run images:build   (sharp: resize + webp + blur)
        ▼
public/images/*.webp             ← آنچه منتشر می‌شود (۰٫۹ MB، در git هست)
src/content/media.generated.ts   ← manifest: src، width، height، blurDataURL
```

`media.generated.ts` **دست‌نویس نیست**؛ با `npm run images:build` بازتولید می‌شود. هر کامپوننت فقط از این manifest می‌خواند، بنابراین:

* `next/image` همیشه `width`/`height` دارد → **هیچ Layout Shift‌ای وجود ندارد** (نسبت تصویر پیش از بارگذاری رزرو شده است)؛
* هر تصویر `blurDataURL` دارد → تصویر از سایهٔ خودش بیرون می‌آید، نه از هیچ؛
* جایگزینی یک عکس **یک گام build است، نه جست‌وجو در کامپوننت‌ها**.

### چرا PNG مادر در git نیست

۱۹ مگابایت فایل میانی، مخزن را برای هر clone کند می‌کند و هیچ‌کس به آن نیاز ندارد. آنچه لازم است (WebP نهایی + manifest) کامیت شده است؛ بازتولید فایل مادر فقط با ابزار تصویر ممکن است.

## ۴. بهینه‌سازی در زمان اجرا

| موضوع | تنظیم |
|---|---|
| کیفیت | `images.qualities: [75, 82, 88]` — ۸۲ برای گالری، ۸۸ برای هدر |
| قالب | `image/avif` سپس `image/webp` (مذاکره با مرورگر) |
| اندازه‌ها | `sizes` در هر فراخوانی صریح است؛ حدس مرورگر پذیرفته نمی‌شود |
| Lazy loading | پیش‌فرض `next/image`؛ فقط تصویر هدر `priority` است |
| نسبت تصویر | از manifest یا `ratio` صریح، نه از رندر ناگهانی |

---

## ۵. جایگزینی با عکس واقعی

۱. فایل اصلی را در `public/images/source/` بگذارید (PNG).
۲. `npm run images:build`.
۳. اگر نام فایل عوض شد، `imageKey` تالار مربوطه را در `src/content/halls.ts` به‌روز کنید.
۴. برای تصویر یک نمونهٔ واقعی، آن را در `media_assets` ثبت کنید و `primary_media_id` نمونه را به آن بدهید؛ کارت نمونه از همان مسیر تصویر می‌گیرد و manifest محلی دیگر دخالت نمی‌کند.
۵. `npm run smoke` — تعداد فایل‌های فونت و اندازه‌ها بررسی می‌شود؛ برای تصاویر، `npm run build` باید بدون هشدار رد شود.

**هیچ کامپوننتی نام فایل تصویر را نمی‌داند.** این همان قاعده‌ای است که برای فونت‌ها هم رعایت شده: یک نقش، نه یک فایل.
